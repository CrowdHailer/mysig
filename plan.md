# Mysig SSG Plan

## Current Asset Fingerprinting

Mysig already has a small explicit asset pipeline. Pages declare assets with
`asset.load(file)` or client bundles with `asset.bundle(module, function)`.
The server runner in `src/mysig/asset/server.gleam` interprets those effects:

- `build_manifest(eff, assets)` walks the `asset.Effect` tree by pattern
  matching on `Done`, `Abort`, `Load`, and `Bundle`.
- For `Load(file, resume)`, it reads bytes with `simplifile.read_bits(file)`,
  splits `filepath.base_name(file)` into `name` and `ext`, hashes the bytes
  with `plinth/browser/crypto/subtle.digest(subtle.SHA256, bits)`, hex encodes
  the digest with `bit_array.base16_encode`, and stores the asset under
  `name <> "." <> digest <> "." <> ext`.
- For `Bundle(module, function, resume)`, it calls `midas/node.do_bundle`,
  hashes the generated JavaScript bytes with the same SHA-256 algorithm, and
  stores the bundle as `function <> "." <> digest <> ".mjs"`.
- The manifest maps original file paths to fingerprinted keys. Server builds
  inject that manifest into HTML with `mysig/dev.manifest`; client code uses
  `mysig/asset/client.load_manifest` to replay the same asset effect and turn
  original paths into `/assets/<fingerprint>`.

The algorithm is content-addressed naming, not timestamp invalidation. Any byte
change produces a different SHA-256 digest and therefore a new URL, so assets
can be served with long-lived immutable cache headers.

## 1. Migrate Mysig To Pamphlet And Midas Continuations

Goal: replace the bespoke `asset.Effect` continuation encoding with the same
`midas/continuation` vocabulary used by Pamphlet, while preserving the explicit
asset declaration model that avoids compiler magic.

Work items:

- Keep `asset.Asset` and `asset.src` as the public value users put in Lustre
  attributes.
- Introduce an `asset.Task(t, a)` alias based on `midas/continuation` so asset
  computations use `continuation.return`, `continuation.then`, and answer type
  terminology instead of `asset.done` and `asset.do`.
- Keep `Load` and `Bundle` as effect boundary constructors internally, but make
  them a runner concern rather than the application-facing abstraction.
- Update server and client runners so the server reifies the answer type to a
  JavaScript `Promise(Result(#(value, manifest), Snag))`, while the browser
  reifies it to `Result(value, Snag)` from the injected manifest.
- Add a Pamphlet renderer integration for content pages. `pamphlet.parse` reads
  front matter and Djot, `pamphlet/lustre` renders into Lustre elements, and the
  Mysig resolver handles URL rewriting through the existing asset manifest.
- Prefer pattern matching in every runner and decoder, following Gleam style:
  narrow data at boundaries, keep variants explicit, and avoid stringly typed
  control flow where a custom type is clearer.

Completion criteria:

- Existing example still compiles with a compatibility shim or a small update.
- A Markdown/Djot page can render through Pamphlet and rewrite local image URLs
  through the Mysig asset runner.
- All source is `gleam format` clean and `gleam test` passes.

## 2. Build Mysig Into A Zola-Scope Static Site Generator

Goal: support the practical scope needed by the two existing sites in `../me`,
plus example ecommerce and blog sites, without becoming a magic compiler.

Core SSG features:

- Content collections from repo files: Markdown/Djot pages with front matter,
  ordered lists, tags, dates, draft flags, slugs, and generated indexes.
- Static route tree: each page builds to `/<path>/index.html`, with passthrough
  static files and fingerprinted assets under `/assets`.
- Layouts as Lustre functions: site code owns the layout and receives typed
  page data, rendered content, navigation, and asset helpers.
- Custom components as Lustre: components are ordinary Gleam functions used
  during SSR. Interactive components declare `asset.bundle(module, function)`;
  Mysig emits a client script and the HTML mount point.
- Data loaders: pure local data, file-backed JSON/TOML, or async HTTP fetches
  for headless CMS use cases. Use package search before adding dependencies;
  current good fits are `jot`/Pamphlet for content, `lustre` for rendering,
  `simplifile` for files, `gleam_json` for JSON, `midas` and `midas_node` for
  effects and bundling.
- Image processing: integrate as an external build step through a runner, not a
  hand-written image codec in Gleam. The best default is a Node adapter around
  Sharp because it is mature, fast, and covers resize, format conversion,
  metadata, and responsive variants. Mysig should model image transforms as
  typed requests and fingerprint the generated bytes using the existing
  SHA-256 asset algorithm.
- Development server: keep lazy route building in dev and eager route walking
  in production so both produce the same artifacts.

Mockup pages for Mysig itself:

- Home: hero "Static sites without compiler magic", code sample showing a
  Lustre page declaring assets, and a live client component counter written in
  Gleam.
- Features: explicit assets, content collections, Pamphlet rendering,
  fingerprinted bundles, image transforms, dev server, static export, and typed
  data loaders.
- About me: explain Mysig as a personal toolkit grown from real sites, with
  links to CrowdHailer, Gleam work, and the design principle of production and
  dev sharing artifacts.
- Donate: state that Mysig is open source, offer GitHub Sponsors/Ko-fi style
  links, and explain donations fund docs, examples, and image pipeline work.

Example sites:

- Ecommerce: build a catalog from a dummy headless CMS JSON endpoint, render
  product listing/detail pages statically, and include a Gleam client component
  for cart state.
- Blog: read Markdown/Djot files from the repo, render article pages, archive,
  tags, RSS-ready metadata, and syntax-friendly article layout.

`../me` migration task:

- Create and use branch `mysig-ssg-migration` in `../me`.
- Migrate the root Jekyll-style site: preserve existing HTML pages, Markdown
  article front matter, index page, article layout, slides pages, canonical
  paths, static media, and Netlify deployment behaviour.
- Migrate `personal/`, currently Zola: preserve `config.toml` base URL, content
  sections, gallery image grid, video log static asset, templates, generated
  Gleam script, and deploy-preview base URL override.
- Mysig SSG is only feature complete for this migration when both sites build
  from source content and output equivalent routes and static assets.

## 3. Future Work

- CI command that runs format, tests, example builds, and a full static export.
- Route diff tool comparing an old generator output directory against Mysig
  output: paths, status, content type, canonical URL, and asset references.
- Image pipeline cache keyed by transform request plus source digest.
- RSS, Atom, sitemap, robots.txt, OpenGraph image generation, and structured
  data helpers.
- Drafts, future-dated posts, taxonomies, pagination, aliases, redirects, and
  broken-link reports.
- Incremental rebuild graph for dev: changed content rebuilds only affected
  pages, layouts rebuild all consumers, assets rebuild by digest.
- Screenshot regression harness for example sites and migrated `../me` sites.
- Launch post and report covering pros and cons of Mysig against Zola:
  explicitness, Gleam type safety, Lustre component reuse, current ecosystem
  gaps, and image pipeline tradeoffs.
- User feedback measurement: track time from fresh clone to first successful
  build, number of manual migration patches needed for `../me`, and whether
  example users can add an image, content page, and client component without
  reading source code.
